# AnimeTrack 页面体验与算法优化路线图

> 建立于 2026-07-25。本文用于安排渐进式优化，每一阶段都应保持可独立验收、可回退。

## 目标

- 页面跳转和按钮操作有及时、可信的反馈。
- 列表筛选、分页和详情返回保持一致状态。
- 连续点击、慢网络和请求乱序不会破坏观看进度。
- 数据增长后，列表、时间线和图谱仍能保持合理响应速度。
- 在现有标签、声优、评分和观看历史基础上逐步加入可解释推荐。

## 第一阶段：操作可靠性与基础反馈

优先解决会造成数据错误或让用户误判操作是否生效的问题。

- [x] 观看进度改为服务端事务内原子增减，避免并发请求覆盖进度。
- [x] 单部作品更新期间禁用进度按钮，并显示处理中状态。
- [x] 为原子增减和历史写入补充集成测试。
- [x] 为主要路由增加 `loading.tsx` 骨架屏。
- [x] 详情加载失败时区分不存在、网络错误和权限错误，并提供重试。
- [x] 统一异步按钮的 `disabled`、`aria-busy` 和处理中提示。

验收标准：

- 快速点击或慢网络下不会出现进度倒退、少记历史或旧响应覆盖新状态。
- 点击导航和异步操作后，用户能立即看到状态变化。
- 测试、TypeScript 检查和生产构建通过。

## 第二阶段：导航与列表状态连续性

- [x] 将状态、声优、标签、排序方式、排序方向和页码统一同步到 URL。
- [ ] 详情页返回后恢复筛选条件、页码和滚动位置。
- [ ] 浏览器前进、后退和刷新时保持相同列表视图。
- [ ] 时间线的视图、分组、排序和搜索条件同步到 URL。
- [ ] 移动端菜单支持点击外部和 Escape 关闭。

验收标准：

- 任意筛选结果都能通过 URL 复制和恢复。
- 列表进入详情再返回时，不丢失上下文。
- 浏览器前进和后退行为符合用户预期。

## 第三阶段：无障碍与交互细节

- [ ] 确认弹窗增加初始焦点、焦点圈定和关闭后的焦点恢复。
- [ ] 排序菜单支持方向键、Enter 和 Escape。
- [ ] 下拉菜单补齐 `aria-expanded`、`aria-controls` 和语义角色。
- [ ] 检查触控区域、键盘焦点样式和移动端横向溢出。
- [ ] 统一空状态、错误状态、重试入口和成功反馈文案。

## 第四阶段：数据接口与查询优化

- [x] 批次 4.1：番剧列表新增轻量概览接口，返回状态数量、观看汇总、热门标签、声优建议和最近观看。
- [x] 批次 4.1：番剧分页接口支持标签和声优筛选，页面不再额外下载全量番剧。
- [x] 批次 4.1：分页计数查询移除不需要的观看历史关联。
- [x] 批次 4.2：首页改用服务端聚合结果，不再为了统计下载全量番剧和历史明细。
- [x] 批次 4.3：为列表封面生成小尺寸 WebP，详情页继续保留原图。
- [x] 批次 4.4：启用并验证 HTTP/2，减少跨境访问时多资源请求的排队。
- [ ] 批次 4.5：仅在加载完成后仍有滚动掉帧时，评估减少模糊和大面积动画。
- [x] 时间线拆分为分页明细、图表聚合和热力图聚合接口。
- [ ] 数据量明显增长后评估把 `lastWatchedAt` 冗余到 `anime` 表。
- [ ] 根据实际数据规模评估标签、声优关联表或 SQLite FTS5 全文搜索。

说明：

当前本地数据规模约为数百部作品，现有查询尚不会构成明显瓶颈。本阶段应以真实数据增长和测量结果为依据，避免提前复杂化。

### 性能优化基线（2026-07-26）

- 数据规模：268 部番剧、268 张本地封面。
- `/api/anime`：响应正文约 413KB，gzip 后实际传输约 146KB，本机首字节约 12ms。
- `/api/anime?page=1&pageSize=12`：响应正文约 22KB，本机首字节约 3ms。
- 当前番剧页同时请求上述两个接口；标签或声优筛选依赖浏览器内的全量数据。
- 服务器 CPU 负载较低、可用内存约 2.2GB，现阶段主要问题不是数据库计算速度，而是跨境网络下的传输体积和重复请求。

批次 4.1 验收标准：

- 页面外观、分页、搜索、状态筛选、标签筛选、声优筛选和排序保持可用。
- 番剧页不再请求 `/api/anime` 全量数据，只请求分页结果和轻量概览。
- 新增、编辑、删除和更新进度后，当前列表与概览统计能正确刷新。
- 轻量概览响应显著小于原全量响应。
- 测试、TypeScript 检查和独立生产构建通过，再进行隔离测试部署。

批次 4.1 实施结果（2026-07-26）：

- 轻量概览正文约 12.6KB，gzip 后实际传输约 6.1KB。
- 概览与当前分页合计约 16KB；相比原先全量与当前分页合计约 156KB，冷加载接口传输量减少接近 90%。
- 使用真实数据验证热门标签与声优筛选，返回数量、分页数量和记录内容正确。
- Lint、TypeScript、13 个测试文件共 82 项测试、独立生产构建和测试部署检查均已通过。
- 用户已确认页面功能与观感正常，提交 `763ae07（优化番剧列表加载）` 已正式发布。

批次 4.2 实施结果（2026-07-27）：

- 首页改为请求单个 `/api/dashboard` 聚合接口，顶部统计、周/月/年趋势、标签、元数据、最近开播、最近在看和活动记录均由服务端生成。
- 聚合接口正文约 29.7KB，gzip 后实际传输约 9.3KB；相比原先全量番剧与近期历史合计约 148.8KB，冷加载接口传输量减少约 94%。
- 番剧总数、累计观看集数和总时长已与原始全量数据逐项比对一致。
- 首页客户端路由代码由 8.04KB 降至 6.8KB。
- Lint、TypeScript、14 个测试文件共 84 项测试、独立生产构建和测试部署检查均已通过。
- 用户已确认首页数字、图表与卡片正常，提交 `b1821c5（优化首页统计加载）` 已正式发布。

批次 4.3 实施结果（2026-07-27）：

- 保留全部原图，新增最高 600×800、质量 82 的 WebP 缩略图；较小原图不会被强行放大。
- 268 张现有封面全部生成成功，0 失败；总大小由原图 79.2MB 降至缩略图 20.9MB，减少 74%。
- 当前番剧第一页 12 张封面实测由约 5.8MB 降至约 1.1MB，减少 81%。
- 番剧网格、列表、侧栏、首页最近作品、图谱和时间线使用缩略图；详情页、编辑预览和首页大背景继续使用原图。
- 新下载封面会自动同步生成缩略图；生成失败时自动回退原图。提供 `npm run covers:thumbnails` 用于批量补建。
- 缩略图使用带版本号的长期不可变缓存；运行中的正式 release 已确认包含 `sharp` 图像处理依赖。
- Lint、TypeScript、14 个测试文件共 85 项测试、独立生产构建和测试部署检查均已通过。
- 用户确认可先提交、后续发现视觉问题再调整，提交 `e261c9a（优化封面加载体积）` 已正式发布。

批次 4.4 实施结果（2026-07-27）：

- Nginx 1.24 已包含 HTTP/2 模块，修改前 TLS ALPN 仅协商到 `http/1.1`。
- AnimeTrack 的 IPv4 与 IPv6 TLS 监听已启用 HTTP/2，并通过 Nginx 配置语法检查和平滑重载。
- 修改后 ALPN 成功协商 `h2`，强制 HTTP/2 请求返回 200；强制 HTTP/1.1 请求仍可正常回退并返回 200。
- 首页聚合接口、健康检查和 WebP 缩略图均已通过 HTTP/2 实际访问验证，Nginx 服务状态保持 `active`。

时间线数据优化实施结果（2026-07-27）：

- 新增 `/api/timeline/overview` 服务端概览接口，统一返回顶部统计、周/月/年趋势、最近 12 个月热力图日计数和去重后的最近观看作品。
- 新增 `/api/timeline/entries` 服务端明细接口，搜索与三种排序均在数据库完成；“时间线”和“列表”视图统一为每页 10 条。
- 明细只返回页面需要的番剧标题、原名、状态、总集数和封面地址，不再向浏览器发送完整番剧简介、标签、声优与备注。
- 右侧改为“最近观看作品”，每部番剧只出现一次并按最后观看时间倒序；搜索时基于全部匹配记录生成，不会只取当前页。
- 更新进度、删除番剧或历史、撤销历史、修改观看时间、导入和恢复备份后，均会刷新新的时间线缓存。
- 固定时间聚合、上海时区、空数据语义、分页、搜索汇总和稳定排序均已补充测试；Lint、TypeScript、16 个测试文件共 92 项测试和独立生产构建通过。
- 使用真实数据核对 110 条历史与 15 部作品，概览总数、明细总数、三种排序和搜索汇总均一致；概览约 7.6KB、首屏 10 条明细约 4.6KB，测试部署健康检查与静态资源检查通过。

## 第五阶段：可解释推荐

第一版不引入机器学习，采用容易调试的内容评分：

```text
推荐分 =
  标签偏好 × 0.35
+ 声优偏好 × 0.20
+ 用户评分相似度 × 0.15
+ 最近观看兴趣 × 0.15
+ 系列连续性 × 0.10
+ 探索奖励 × 0.05
```

- [ ] 先对库内“想看”和未开始作品生成推荐。
- [ ] 最近观看的权重高于较早历史，看完和高评分为正反馈，弃坑为负反馈。
- [ ] 加入已看作品、重复条目和错误季度等硬过滤。
- [ ] 在页面展示推荐理由，例如“因为你最近看完了 3 部奇幻作品”。
- [ ] 再评估从 Bangumi 获取库外候选，并保留人工确认入口。
- [ ] 使用点击、开始观看、看完和忽略作为离线评估信号。

## 实施约定

- 每次只推进一个可验证的小批次，并在本文更新完成状态。
- 涉及界面改动时默认不启动浏览器；完成后运行相称的测试、类型检查或生产构建。
- 算法优化先记录基线数据和查询计划，再决定是否增加缓存、索引或数据表。
- 数据写入相关改动必须优先补充事务和回滚测试。
